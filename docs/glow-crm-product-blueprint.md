# Glow CRM Pro — продуктовый и архитектурный blueprint (версия для коммерциализации по цене €350 за копию)

## 1) Исполнительное резюме

**Цель:** превратить текущий концепт Glow CRM в **продаваемый, практически применимый продукт** для салонов красоты и health/wellness-студий в Чехии, ЕС и СНГ.

**Коммерческая модель первой линии:**
- Одноразовая продажа «коробочной» копии: **€350**.
- Дополнительный MRR (рекомендуется):
  - Хостинг/поддержка/обновления: €19–€49/мес.
  - Платные модули: WhatsApp automation, зарплаты, склад, AI-планировщик.

**Продуктовая идея:**
- Быстрый запуск салона за 1 день.
- Запись клиента < 60 секунд.
- Минимум рутины для админа: авто-напоминания, автозаполнение расписания, авто-аналитика.
- Правовая готовность: GDPR by Design + дорожная карта EET 2.0 (CZ).

## 5) Сценарии и бизнес-логика (E2E)

## A. Первичная настройка салона (Onboarding)
1. Регистрация салона.
2. Выбор страны/валюты/часового пояса.
3. Импорт услуг и мастеров (CSV).
4. Настройка графиков + буферы.
5. Публикация страницы онлайн-записи.

**KPI:** Time-to-value < 45 мин.

## B. Запись клиента
1. Клиент выбирает услугу.
2. Система фильтрует мастеров по компетенциям.
3. Алгоритм слотов учитывает длительность + буфер + ресурс.
4. Подтверждение и отправка уведомлений.

**KPI:** завершение записи < 60 сек.

## C. Визит и оплата
1. Check-in клиента.
2. Фиксация фактически оказанных услуг.
3. Оплата (card/cash/online tokenized).
4. Закрытие визита и запуск post-visit цепочки.

## D. Retention automation
- После 60 дней без визита → автооффер + напоминание.
- После визита через 2 часа → запрос отзыва.

## E. Off-line/ошибки
- Нет сети: очередь событий в local store.
- Восстановление сети: idempotent replay.
- Конфликты: server-authoritative merge policy.

## 6) Архитектура (масштабируемость, отказоустойчивость, производительность)

## Рекомендованный стек
- **Frontend:** Next.js (App Router) + TypeScript + TanStack Query + Zustand.
- **Backend:** NestJS + TypeScript.
- **DB:** PostgreSQL 16 (tenant_id everywhere).
- **Cache/Queue:** Redis + BullMQ.
- **Storage:** S3-compatible.
- **Observability:** OpenTelemetry + Prometheus + Grafana + Sentry.
- **Infra:** Docker + Terraform + AWS (ECS/RDS/ElastiCache) или аналог.

## Архитектурный стиль
- Этап 1: **Модульный монолит** (быстрее вывода на рынок).
- Этап 2: выделение сервисов (notifications, billing, analytics, integrations).

## Multi-tenancy
- Shared DB + strict row-level isolation (tenant_id).
- Опционально PostgreSQL RLS для критичных таблиц.
- Tenant-aware кеши и rate limits.

## Надежность
- SLA target: 99.9% (Base), 99.95% (Scale).
- Retry policies, circuit breaker, dead-letter queue.
- PITR backup + ежедневные snapshots.
- Blue/green deploy для безоткатных релизов.

## Производительность
- p95 API < 300ms (календарные read-операции).
- Индексы: (tenant_id, starts_at), (tenant_id, client_id), (tenant_id, staff_id, date).
- Read replicas для аналитики.

## 7) Модель данных (ядро)

- `tenants` — салоны.
- `users` — аккаунты.
- `roles`, `user_roles` — RBAC.
- `clients` — клиенты.
- `staff_profiles` — мастера.
- `services` — услуги.
- `resources` — кабинеты/оборудование.
- `appointments` — записи.
- `appointment_events` — аудит жизненного цикла.
- `payments` — оплаты.
- `inventory_items`, `inventory_movements` — склад.
- `consents` — GDPR-согласия.
- `fiscal_receipts` — фискальные записи (вкл. EET-адаптер).
- `automation_rules`, `automation_runs` — маркетинг и триггеры.

## 8) Безопасность и compliance

## GDPR by Design
- Data minimization по умолчанию.
- Явные согласия с версией политики.
- DSR-инструменты: экспорт JSON/PDF, удаление/анонимизация.
- Audit trail всех чувствительных действий.
- Encryption at rest + TLS 1.2+ in transit.

## Чехия / EET 2.0-ready
- Фискальный адаптер в отдельном модуле.
- Offline queue чеков + гарантированная последующая отправка.
- Лог сверки оплат и фискальных ответов.

## СНГ-фокус
- Интеграционная шина для Telegram/WhatsApp/локальных PSP.
- Шаблонизация сообщений и legal-consent логика рассылок.

2. **Definition of Done = код + тесты + метрики + документация + security check.**
3. **Любая фича проходит сценарии happy path + edge cases + failure modes.**
4. **Ни одного «магического» решения без обоснования в ADR.**

8. **Postmortem без поиска виноватых, только системные выводы.**

## 12) Полный перечень критических edge-cases

- Двойное бронирование одного мастера.
- Частичная предоплата и отмена.
- Перенос записи при недоступности мастера.
- Изменение длительности услуги «на лету».
- Работа филиалов в разных часовых поясах.
- Race condition при массовом бронировании пиковых слотов.
- Потеря сети во время оплаты.
- Повторные webhook-события (idempotency key).
- Конфликт согласий GDPR и маркетинговой рассылки.
- Откат релиза при деградации p95.
- Пиковая нагрузка (акции/черная пятница).
- Частичная недоступность внешних интеграций (PSP/messenger).
